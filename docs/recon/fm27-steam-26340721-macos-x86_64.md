# FM27 Steam 26340721 on macOS: the Intel half (x86_64)

Static work only. Nothing was run on an Intel game. Every value below comes from the x86_64 slice of
`game_plugin` (LC_UUID `0981AB31-AC3B-3D93-944F-47FE4B59CD9E`), compared with the arm64 slice
(`F4540355-2186-39CB-9119-C706A6A35346`). The slice was cut with `lipo -thin x86_64` from the installed
file (read only) and disassembled with `llvm-objdump`. RVAs are file addresses of that slice, as in the
arm64 notes.

## Summary

Only two things in the arm64 profile were missing from the Intel profile, and both are now located:

| Value | Where it goes | Proposed x86_64 value | Confidence |
|---|---|---|---|
| `officials` (begin, end pair) | build profile, top level | `0x5C89240` | high |
| `[human_manager]` flags | build profile, section | `flags = 0x3FC`, `person_shift = 0x340`, class `N2db16HUMAN_NON_PLAYERE` | high |

Everything else FM Lens reads on arm64 (nation profile, languages, rivals and affiliates, cohesion,
likes and dislikes, official fields) lives in `profiles/fm27/layout-macos.toml`, which both architectures
load. Those struct offsets are the same on x86_64 (evidence below), so Intel gets those readers as soon as
the build profile names the officials array. No layout change is needed.

## Inventory (step 1)

How the profile is chosen: `crates/fmlens-core/src/profile.rs` lists `BUILDS` (all `steam-*` and
`gamepass-*` tomls) and `LAYOUTS` (`layout-macos.toml` on macOS). `profile_for` matches the
`PluginFingerprint::MachO { uuid }` read from the mapped headers, so each architecture has its own build
profile and the shared layout.

`profiles/fm27/steam-26340721-macos-x86_64.toml` exists. It holds: `current_date = 0x5C69700`,
`retirement_manager = 0x5C5FEF0`, `[plugin] uuid`, and `[arrays]` players `0x5C891C8`, staff `0x5C89210`,
clubs `0x5C89380`. It has no `officials` and no `[human_manager]`.

arm64-only items in `steam-26340721-macos-arm64.toml`:

- `officials = 0x56D2E90` (build profile, unverified on Intel).
- `[human_manager]` flags `0x3FC`, `person_shift = 0x340`, class name.

Everything else in the arm64 profile (date, retirement manager, three arrays) already has an Intel value.
The Intel values were found by counting RIP-relative loads, not by a twin function. I re-checked them
below.

The layout sections marked "Read on Steam 26340721 arm64" in `layout-macos.toml` (`[language]`,
`[national]`, `[cohesion]`, `[official]`, club `relations`/`links`) are struct offsets, not RVAs. They were
never measured on Intel. I checked them against the Intel slice below.

## Proposed values and evidence

### officials = 0x5C89240 (high)

The arm64 pair is `0x56D2E90` (begin) and `0x56D2E98` (end). It sits `0x78` above the players pair
(`0x56D2E18`). On Intel the players pair is `0x5C891C8`, and `0x5C891C8 + 0x78 = 0x5C89240`.

Evidence, in order of strength:

1. Three arm64 functions loop over the officials array. Each has an exact Intel twin that loads
   `0x5C89240` and `0x5C89248`:
   - arm64 `0x19AA370` (filter officials by `[official+0x38]` equal to a nation, guarded by a `[x8,#0x60]`
     test) is Intel `0x1AFDC26`: same guard (`cmpq $0,0x60(%rax)`), same `0x38(%r13)` nation compare
     against `0x60(%rcx)`.
   - arm64 `0x1C5CBA0` (for each official, calls a vtable slot `0x1D0` on `[x27+0x128]`, tests `0x140 & 0x1000`,
     picks `0x110` or `0x118`, reads `[x+0x170]`, `[x+0x128]`, and the club's byte `0xB9`) is Intel
     `0x1E0B183`: the same offsets `0x128`, `0x1D0`, `0x140`, `0x110`, `0x170`, `0x128`, `0xB9`.
   - arm64 `0x2904884` (for each official call `f(this, official)`) is Intel `0x2B81CB3`, calling `0x2B82A70`.
     That callee reads `[official+0x38]` (nation), `[nation+0xF8]` (continent, as `[national] continent`),
     and a vector at `[official+0x80]`/`[+0x88]`, exactly as arm64 `0x29052C4` does.
2. The shutdown function that frees every global vector. arm64 `0x118A1A0` region frees pairs at
   `0xE18` (players), `0xE60` (staff), `0xE90` (officials), `0xFD0` (clubs). Intel `0x10E9DE7` region frees
   `0x5C891C8`, `0x5C89210`, `0x5C89240`, `0x5C89380` in the same order and at the same spacing (staff
   `+0x48`, officials `+0x78`, clubs `+0x1B8` from the players).
3. Intel loads of `0x5C89240` outside the shutdown: 4 (twins above plus `0x1AFE4E2`, a second filter that
   compares the nation's `0xF8` field).

This also confirms the three existing Intel arrays (players, staff, clubs) by the same shutdown order and
spacing. Confidence for those: high.

Element layout: pointers to `db::OFFICIAL` objects. `[official]` offsets in the layout are used as they are;
`+0x38` nation and `+0x80/0x88` vector are confirmed on Intel above. The rest (`+0x20/0x28/0x30` names,
`+0x58` birth date, `+0x114/0x116/0x118`, `+0x134` UID) were not individually compared, but the class is
laid out by the same compiler and the twin accessors agree on every offset I could compare (see layout
section). Medium-high.

### [human_manager] (high)

`become_unsackable` is at `0x573290F` in the Intel slice (arm64 `0x5155B12`). Its handler is `0x25643B0`
(arm64 `0x238A17C` region):

- `0x25643E1: movl $2, %esi`, then calls `0x2564440` (arm64 sets `w1 = 2`, calls `0x238A1FC`).
- `0x2564440` finds the selected human manager exactly as arm64 `0x239448C` does: `0x256EAC0` loops a
  16-byte table for the code `0x4868756D` ('mhuH'), then calls vtable slot `0x40` (must return 1) and
  vtable slot `0x6F0` (the manager object). arm64 uses the same slots `0x40` and `0x6F0`.
- `0x25644AF: andl %r12d, 0x3FC(%rbx)` and `0x25644B8: orl %r12d, 0x3FC(%rbx)` (arm64 `bic`/`orr` on
  `[x21,#0x3FC]`). Flags offset `0x3FC`, not shifted again, same as arm64.
- `0x25644BF: addq $0x548, %rbx` equals arm64 `add x0, x21, #0x548` after the store.

`person_shift = 0x340` is a property of the object layout (HUMAN_NON_PLAYER vs the staff person block), the
same class on both slices. The RTTI name `N2db16HUMAN_NON_PLAYERE` is present in the Intel slice
(`__cstring` `0x5968A5F`). The vtable address differs between slices, so the profile must not carry one; the
profile stores only the mangled class name, which is arch independent.

Also confirmed: `squad_registration_anytime` and the other bit masks use the same `0x3FC` word, since they
share the same handler helper.

### Existing Intel values, re-checked

- `[arrays]`: high, see the shutdown comparison above.
- `current_date = 0x5C69700`: medium-high. A function at `0x1DE85E3` loads the retirement-manager global,

  call it verified.

## Struct offsets checked on Intel (layout-macos.toml stays shared)

Twins found where the Intel code touches the same fields at the same offsets:

- Nation (`[national]`): arm64 nation loader stores bytes `0x1EC..0x1F4` then `lea 0x140(obj)` (arm64
  `0x2CA8948..0x2CA8970`); Intel `0x2FA6E79..0x2FA6ECE` stores `0x1ED..0x1F4` and `lea 0x140(%rsi)`:
  population block and dual-nationality bytes (`0x1EC`, `0x1F1`) agree. A copy function (arm64 `0x6C2200`,
  Intel `0x6F3DF0`) copies `0x86C` (u32), the vector at `0x870` (4-byte elements), the vector at `0x888`
  (24-byte elements), then `0x8A0`: `[national] joined_fifa 0x86C`, `founded 0x870` area agrees.
- Nation continent `0xF8`, official nation `0x38`: Intel `0x2B82A8D..0x2B82A95` = arm64 `0x29052E4..0x29052EC`.
- Club: byte `0xB9` (women), `0x170`, `0x128`, `0x110` agree (Intel `0x1E0B1BF..0x1E0B213`).
- Player copy function (arm64 `0x170CE0`, Intel `0x17B010`): same fields at `0x290`, `0x2A0`, `0x2B0`,
  `0x310` (vector of 8-byte elements), `0x328`, `0x338` (a pointer, the layout's `[language] player`),
  `0x340`, `0x348`, `0x358`, `0x365/0x378`. `[language] player = 0x338` agrees.
- Team/person: arm64 `[x27,#0x128]` + vtable `0x1D0` = Intel `0x128(%r12)` + `0x1D0(%rax)`.

Not individually twinned: `[language] staff = 0x1B8`, `[cohesion]` (relations record list `0x18`),
club `relations 0x48` and `links 0x118`, `[national] points 0x378`, `ranking 0x570`, `rivals 0x48`,
`languages 0x48`. They sit in classes whose other fields all matched. The compiler (clang, Itanium ABI),
the data model (LP64) and the pointer width are identical, and I found no `#ifdef`-style divergence in any
twin. Confidence: medium-high for these, high for the ones listed above.

## Work permits (6 November 2026)

Found statically in the same slice, then checked in the game (below). The arm64 values are in `steam-26340721-macos-arm64.toml` and
[fm27-call-shapes.md](fm27-call-shapes.md) section 1.

| Value | arm64 | x86_64 | Confidence |
|---|---|---|---|
| `transfer_manager` | `0x56A49F8` | `0x5C5DE80` | high |
| `[calls] set_work_permit` | `0x2D85294` | `0x309A010` | high |
| `[calls] find_work_permit` | `0x2DDD12C` | `0x30FC8E0` | high |
| `[calls] remove_work_permit` | `0x2DC0210` | `0x30D8D20` | high |

How they were found:

- **The game's editor action for work permits:**
  - The analytics strings `add_work_permit` (`0x5732982`) and `remove_work_permit` (`0x5732992`) are each loaded once, at `0x25694BE` and `0x25695FA`.
  - Both loads are in `0x2569350`, the twin of the arm64 handler `0x238F110`.
  - Like the arm64 handler, it looks up the keys 'dref' (`cmpl $0x64726566`) and 'tick' (`cmpl $0x7469636b`).
  - It gets the player through identity vtable slot `0x6E0`.
  - It takes the identity block at the player plus the virtual-base offset at vtable `-0x18`.
  - It picks the team from the contract (`[P+vbase+0x78]`, slot `0x90`) or from slot `0x230`.
- **`transfer_manager`:**
  - The handler loads it at `0x2569424` (`movq 0x5c5de80(%rip)`).
  - The same global is loaded in 985 places.
  - The RTTI name `16TRANSFER_MANAGER` (the layout's class check) is in the slice at `0x599442E`.
- **Revoke ('tick' true):**
  - `callq 0x30FC8E0` (TM, identity, team) at `0x25695C8`.
  - A negative result skips the rest. Otherwise the record is `[[TM+0x720] + 8 * index]`.
  - Then `callq 0x30D8D20` (TM, identity, record) at `0x2569658`.
- **Grant ('tick' false):** `callq 0x309A010` (TM, identity, team, 0, 0) at `0x25696A8`.

The bodies match the arm64 shapes:

- **`0x30FC8E0` (find):**
  - Returns -1 unless the identity's byte `+0x18` has bit `0x4`.
  - Takes the nation from the team: kind byte `+0x2F`; for a club, `0xEC1140(club)`; otherwise `[team+0x30]+0x170`.
  - Binary-searches the records `+0x720/+0x728` by the u32 at record `+0x08` against identity `+0x08`.
  - Called from 26 places.
- **`0x30D8D20` (remove):**
  - If the record's date at `+0x12` (year `+0x14`, `0x76C` unset) is set, takes the record out of the ESC list `+0x780/+0x788`.
  - Then takes it out of the records `+0x720/+0x728` and frees it.
  - Clears bit `0x4` of the identity flags (`+0x18`) when the player has no record left.
  - Called from 4 places.
- **`0x309A010` (grant):**
  - Arguments are saved as `rdi` TM, `rsi` identity, `rdx` team, `ecx` force, `r8d` esc.
  - Reads the team's kind `+0x2F`, `+0x30`, `+0x170`.
  - Sets or clears the ESC flag at record `+0x16`, dates it at `+0x12`, and keeps the ESC list at `+0x780`.
  - Writes the unset date `0x76C0001` at `+0x12` when the slot ends.
  - Called from 14 places.

The `[work_permit]` layout in `layout-macos.toml` stays shared: records `0x720`, record id `0x08`, ESC date `0x12` and flags `0x16` are the offsets these functions use. The record size (`0x18`) is allocated in a callee and was not compared.

The Intel profile has no other calls. Only Work permit becomes available on Intel. Every other game action also needs RVAs that are still arm64-only.

The first Revoke failed with "it cannot make calls on this Mac", because the bridge made calls on arm64 only.

- It now makes them the System V way too: the first six arguments in `rdi`, `rsi`, `rdx`, `rcx`, `r8` and `r9`, the rest on the stack, the result in `rax`.
- The call sites above pass their arguments in that order.
- A unit test calls a twelve-argument function through it on both architectures.
- On Intel it refuses a call with an indirect result (`x8` on arm64). No Intel call needs one yet.
