The database root is constructed in place: `0x2AE28` passes `0x5C890C8`; `0x10F23C0` retains it in rbx and passes it to `0x10F4840`. The latter stores typed table pointers at offsets 0, 0x18 and 0x98 for AWARD, COMP and TEAM_BASE. The RTTI chains are name `0x5964E6A` -> typeinfo `0x5B5B670` -> vtable `0x5B59B50` (AWARD), `0x5964ECE` -> `0x5B5B6B8` -> `0x5B59CB8` (COMP), and `0x596511A` -> `0x5B5B820` -> `0x5B5A3C0` (TEAM_BASE). Chained rebases use the low 36 bits as the target RVA. This is independent evidence, not an assumed constant slide between architectures.

### Core and helper ABI audit

`Session::game_actions`, the action implementations in `game_calls.rs`, `tactics.rs`, and the competition/award readers already operate on profile values on both macOS architectures. There is no ARM64-only gate to remove from these paths. Shared `layout-macos.toml` remains appropriate: the Intel builder at `0x2567D60` initializes the 0x70-byte STARTING_LOAN with the same offsets, sentinels and defaults; person/identity virtual-base offsets are read from vtable `-0x18`. Identity slots `0x398`, `0x3A0`, `0x6E0` and human-manager slot `0x6F0` are unchanged in the paired editor paths. The existing human-manager section is identical to ARM64. No Windows offsets are borrowed.

On x86_64 the bridge flattens Step's twelve scalar slots into rdi, rsi, rdx, rcx, r8, r9, then six stack qwords; return is rax (only al for bool). The paired signing caller `0x2566F92..6FAC` confirms all six register arguments, including person before team. End contract `0x2569076..90A1`, withdrawal `0x25690A6..90C1`, release `0x25690C6..90F9`, and cancellation `0x25665EF..6616` confirm the stack argument order, including the fourth argument's word-sized kind. Zero-valued narrow arguments are safely represented by zero qwords. Training injury caller `0x1B7DBE2..DC1F` uses cause 3 and registers/stack in the same order; every later optional argument FM Lens passes is zero.

All compound objects are passed by pointer: STARTING_LOAN, maps, Values, reference vectors and held-offer slots. There are no by-value aggregates or hidden struct returns among these 24 calls. Date construction explicitly takes (type, output Value, raw date), and struct construction takes (output Value, source map). None of the 24 calls passes a result place through `Step.indirect`, but the Intel bridge now supports it anyway, so every call shape the ARM64 path can express also runs on x86_64: a nonzero `indirect` becomes the hidden first argument in rdi under System V, the twelve ordinary arguments move up one slot (the first five in rsi to r9, the rest spilled in order to the stack), and the function hands the place back in rax. The capability reply sets its indirect bit on x86_64 as well as arm64, so a helper built before this change (which reports no indirect support and refuses such a step) is still told apart by the app. Existing helper discovery/allowlist checks remain in place: an older helper must refuse missing calls and the app must keep those controls unavailable until a rebuilt Intel helper is loaded.

Cleanup matters: `refs_drop` must be `0x48FB750`, not its pointer-to-pointer callee `0x48FD4A0`. The latter appears directly in editor cleanup because the editor already takes the address of its local vector pointer. FM Lens passes the vector itself, so it needs the wrapper. `map_drop` has the same wrapper pattern. Ref-drop uses the object's destructor slot `+8`, while Value-drop uses the type object's slot `+0x18`; these are distinct operations.

A pinned Intel profile test asserts every call and every new profile value, and retains the human-manager assertions. A bridge unit test exercises explicit scratch outputs, passing one call's result into the next, skipped steps on refusal and cleanup afterward. The existing twelve-argument ordering test covers the register/stack boundary. Two more bridge tests pass a 24-byte object result (returned in memory by every C ABI) through `invoke` and through a `Step` that returns into scratch, with all twelve ordinary arguments checked. Run the bridge tests with `--target x86_64-apple-darwin` to exercise System V, rather than relying only on native ARM64 tests.

Expected newly available sections/actions with this profile and a rebuilt Intel helper: competitions, awards, adding injuries, starting and ending loans, free-agent signing, Move/Swap transfers, releasing players, future signing/cancellation, Max tactics, and human-manager Change club. Existing capability, career, entity, contract, supported-build and editor-enabled checks still apply. ARM64's known limits, especially linked transfer history and simulation consistency, still apply. These are enabled mappings awaiting live Intel validation, not a parity-validation certificate.

## Proposed values and evidence

### officials = 0x5C89240 (high)

The arm64 pair is `0x56D2E90` (begin) and `0x56D2E98` (end). It sits `0x78` above the players pair
(`0x56D2E18`). On Intel the players pair is `0x5C891C8`, and `0x5C891C8 + 0x78 = 0x5C89240`.

Evidence, in order of strength:

1. Three arm64 functions loop over the officials array. Each has an exact Intel twin that loads
   `0x5C89240` and `0x5C89248`:
   - arm64 `0x19AA370` (filter officials by `[official+0x38]` equal to a nation, guarded by a `[x8,#0x60]`
     test) is Intel `0x1AFDC26`: same guard (`cmpq $0,0x60(%rax)`), same `0x38(%r13)` nation compare
     against `0x60(%rcx)`.
   - arm64 `0x1C5CBA0` (for each official, calls a vtable slot `0x1D0` on `[x27+0x128]`, tests `0x140 & 0x1000`,
     picks `0x110` or `0x118`, reads `[x+0x170]`, `[x+0x128]`, and the club's byte `0xB9`) is Intel
     `0x1E0B183`: the same offsets `0x128`, `0x1D0`, `0x140`, `0x110`, `0x170`, `0x128`, `0xB9`.
   - arm64 `0x2904884` (for each official call `f(this, official)`) is Intel `0x2B81CB3`, calling `0x2B82A70`.
     That callee reads `[official+0x38]` (nation), `[nation+0xF8]` (continent, as `[national] continent`),
     and a vector at `[official+0x80]`/`[+0x88]`, exactly as arm64 `0x29052C4` does.
2. The shutdown function that frees every global vector. arm64 `0x118A1A0` region frees pairs at
   `0xE18` (players), `0xE60` (staff), `0xE90` (officials), `0xFD0` (clubs). Intel `0x10E9DE7` region frees
   `0x5C891C8`, `0x5C89210`, `0x5C89240`, `0x5C89380` in the same order and at the same spacing (staff
   `+0x48`, officials `+0x78`, clubs `+0x1B8` from the players).
3. Intel loads of `0x5C89240` outside the shutdown: 4 (twins above plus `0x1AFE4E2`, a second filter that
   compares the nation's `0xF8` field).

This also confirms the three existing Intel arrays (players, staff, clubs) by the same shutdown order and
spacing. Confidence for those: high.

Element layout: pointers to `db::OFFICIAL` objects. `[official]` offsets in the layout are used as they are;
`+0x38` nation and `+0x80/0x88` vector are confirmed on Intel above. The rest (`+0x20/0x28/0x30` names,
`+0x58` birth date, `+0x114/0x116/0x118`, `+0x134` UID) were not individually compared, but the class is
laid out by the same compiler and the twin accessors agree on every offset I could compare (see layout
section). Medium-high.

### [human_manager] (high)

`become_unsackable` is at `0x573290F` in the Intel slice (arm64 `0x5155B12`). Its handler is `0x25643B0`
(arm64 `0x238A17C` region):

- `0x25643E1: movl $2, %esi`, then calls `0x2564440` (arm64 sets `w1 = 2`, calls `0x238A1FC`).
- `0x2564440` finds the selected human manager exactly as arm64 `0x239448C` does: `0x256EAC0` loops a
  16-byte table for the code `0x4868756D` ('mhuH'), then calls vtable slot `0x40` (must return 1) and
  vtable slot `0x6F0` (the manager object). arm64 uses the same slots `0x40` and `0x6F0`.
- `0x25644AF: andl %r12d, 0x3FC(%rbx)` and `0x25644B8: orl %r12d, 0x3FC(%rbx)` (arm64 `bic`/`orr` on
  `[x21,#0x3FC]`). Flags offset `0x3FC`, not shifted again, same as arm64.
- `0x25644BF: addq $0x548, %rbx` equals arm64 `add x0, x21, #0x548` after the store.

`person_shift = 0x340` is a property of the object layout (HUMAN_NON_PLAYER vs the staff person block), the
same class on both slices. The RTTI name `N2db16HUMAN_NON_PLAYERE` is present in the Intel slice
(`__cstring` `0x5968A5F`). The vtable address differs between slices, so the profile must not carry one; the
profile stores only the mangled class name, which is arch independent.

Also confirmed: `squad_registration_anytime` and the other bit masks use the same `0x3FC` word, since they
share the same handler helper.
