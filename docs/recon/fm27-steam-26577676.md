# FM27 Steam build 26577676 (27.0.1)

An update on Steam on 12 November 2026 (app 4530370), two days after 27.0.1. On macOS `fm.app` reads version
27.0.1.2503222, and Steam fetched about 6.8 MB for it.

The update rebuilt game_plugin on every platform: both macOS halves have another LC_UUID and the Windows DLL another
size of image and link timestamp, so FM Lens opened the build read-only. Every function and static FM Lens uses sits
where build 26385295 has it, on every platform. On macOS the two constants it reads from `__TEXT` sit 0x30 further in
both halves (see "What moved on macOS"). The Windows profile is build 26385295's under the new size and timestamp; the
two macOS profiles are build 26385295's under the new UUIDs with those two constants moved.

## The binaries

| | Build 26577676 | 27.0.1 (26385295) |
|---|---|---|
| macOS arm64 LC_UUID | `A8550B47-FDE0-3D0D-A6CB-1B63DEE8DA19` | `2A2D0ED6-324E-3D0D-A27D-10AEDBD0E270` |
| macOS Intel LC_UUID | `DD0EE157-4C9C-31A7-81DD-0D1122E62FC7` | `94CDDC80-8474-327A-85E0-E4FF95DC6893` |
| macOS arm64 image size | `0x5990000` | `0x5990000` |
| Windows size of image | `0x185FA000` | `0x17CB9000` |
| Windows link timestamp | `0x6AF38E5C` | `0x6AE8B5A4` |

The arm64 segments are `__TEXT` 0x554C000, `__DATA_CONST` 0x1F4000 from 0x554C000, `__DATA` 0x9C000 from 0x5740000 and
`__LINKEDIT` from 0x57DC000. The Intel ones are `__TEXT` 0x5AE3000, `__DATA_CONST` 0x1F3000, `__DATA` 0x98000 from
0x5CD6000.

The Windows DLL is 0x941000 larger in memory. Most of it is the protection's own section (`.00cfg` here, 0x12830F88
long), which is laid out anew on each build. The code is still the first section at RVA `0x1000` (`.ecode`,
0x4BDC000 long), the read-only data follows at `0x4BDD000` and the statics are in the section at `0x578C000`.

## What shows the functions and statics stayed

No copy of build 26385295's file was kept, so the two were not compared byte for byte. The new file was read against
build 26385295's profiles instead:

1. All 26 functions FM Lens has the game run are function starts (`LC_FUNCTION_STARTS`) in both halves. A function
   starts every 760 bytes or so, so 26 addresses of a build that had moved would not all land on one.
2. The code still calls each of them, and still loads each static, in numbers that agree across the two halves:
   `set_work_permit` 14 calls in each, `find_work_permit` 26, `end_contract` 25, `withdraw_offers` 18, `leave_team` 53,
   `cancel_offer` 45, `start_loan` 2, `sign_free_agent` 2, `maximise_tactics` 1. The Intel half loads the date in
   7,729 places, the players' array in 185, the staff's in 18 and the clubs' in 105, where 27.0.0 had 7,730, 184, 18
   and 105.
3. The call sites the profiles' notes name are where they were. On arm64 the instruction at `0x25D974` calls
   `date_type` and the ones at `0x25D980` and `0x25D994` call `date_value` and `map_insert`; `0x239BC7C` calls
   `cancel_offer` and `0x239BC94` `drop_dated_transfer`; `0x2621018` calls `end_contract`; the editor's functions at
   `0x239C64C`, `0x239D64C` and `0x239EBC8` call `sign_free_agent`, `start_loan`, and `end_contract`,
   `withdraw_offers` and `leave_team`. On Intel `0x2573CB8` calls `find_work_permit`, `0x2573D48`
   `remove_work_permit`, the instruction at `0x2573B14` loads the transfer manager, and the STARTING_LOAN builder at
   `0x2572450` takes its vtable and calls `start_loan`.

`entity_changed` has no direct call, as before: the game reaches it through GAME_UI's virtual slot.

### Windows

The same reading of the new DLL against `steam-26385295.toml`:

1. 20 of the 26 functions start a function in the exception directory. `remove_work_permit`, `withdraw_offers`,
   `map_drop` and `map_insert` are a jump into the protected code, and `date_value` and `ref_copy` are leaves with no
   unwind entry.
2. The callers the profile's notes name still call them. The game's editor calls `withdraw_offers` at `0x2A97CBC`,
   `leave_team` at `0x2A97CF2` and `cancel_offer` at `0x2A952BD`; its work permit action at `0x2A97F70` calls
   `find_work_permit`, `remove_work_permit` and `set_work_permit`; its loan action at `0x2A96770` calls `start_loan`;
   the training injuries at `0x2ECA3B0` call `add_injury`; `become_unsackable` at `0x2F3C1D0` still works on `+0x3FC`.
3. The code loads each static in numbers close to the Intel half's on macOS: the date in 7,220 places, the players'
   array in 167, the staff's in 20, the clubs' in 95, the teams' table in 1,080, the transfer manager in 959.
4. The data the profile points at is what its notes say: the date for none reads 1 January 1900, the STARTING_LOAN
   vtable's entries point into the code, and its 16 default bytes are `FFFFFFFF 00000000 FFFFFFFF FFFFFFFF`.

## What moved on macOS

The reading above covers functions and statics. It missed the two constants a game action reads out of `__TEXT`, and
the first profiles carried build 26385295's addresses for them. The checks in the game caught it: a loan FM Lens
started on Apple silicon read back with a future fee of 33,619,968, and End loan refused it.

| | arm64 | Intel | Build 26385295 (arm64, Intel) |
|---|---|---|---|
| `starting_loan.defaults` | `0x542ACF0` | `0x59DF060` | `0x542ACC0`, `0x59DF030` |
| `work_permit_check.no_date` | `0x538A470` | `0x59349A0` | `0x538A440`, `0x5934970` |

Each is read from the game's own code. The editor's loan action loads its 16 default bytes with `ldr q0` from
`0x542ACF0` at `0x239D6B0` on arm64 and with `movaps` from `0x59DF060` at `0x25724C1` on Intel; both hold
`FFFFFFFF 00000000 FFFFFFFF FFFFFFFF`. `set_work_permit` passes the date for none from `0x538A470` at `0x2D94390` on
arm64 and from `0x59349A0` at `0x30A2D55` on Intel; both hold `01 00 6C 07`, 1 January 1900. The old addresses now
hold other data: `01000101 00000000 02010000 00000000` and the text `PLAYER_SALARY_CA` on arm64.

FM Lens now reads both back before it uses them: it starts no loan unless the 16 bytes are the unset fees, and does
not ask whether a player needs a work permit unless the date is 1 January 1900.
